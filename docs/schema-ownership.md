# 数据库结构所有权与发布契约

数据库迁移是正常安装、升级流程的一部分，不是独立运维流程。内网只运行
`install.sh --finish` 或 `upgrade.sh`；脚本在切换新模块前自动执行对应迁移，失败则停止升级。

## 唯一所有者

同一张表只能由一种迁移工具、一个模块管理：

- `dbdog-server` 的 Goose migrations 管理 server 领域的 PostgreSQL 表。
- `dbdog-web` 的 Drizzle migrations 管理身份、OAuth 与控制台领域的 PostgreSQL 表。
  当前 `api_keys`、`dashboards` 虽被 server 只读访问，结构所有者仍是 web。
- ClickHouse `obs` 及租户表只由 `dbdog-server` 的版本化 blueprint 推进。

“多个服务访问”不等于共同拥有。新增交叉访问表时，以负责写入和业务不变量的模块为唯一
结构所有者；其他模块只消费，不得再写一套 DDL 或迁移。

## 发布与兼容

迁移文件随其所有者模块进入产物，产物内带校验清单。升级已安装模块时，配置缺失、迁移
文件被修改或迁移执行失败都会发生在 `current` 切换之前，并使正常升级直接失败。

跨模块结构变更必须使用 expand/contract：先发布向后兼容的新增结构，再升级消费者，最后
在后续发布删除旧结构。不要依赖同一次升级中的偶然先后顺序承载破坏性兼容。

迁移历史只增不改。数据库迁移通常不可随二进制软链回滚；执行升级前仍应按环境的数据
保护策略完成备份或快照。
