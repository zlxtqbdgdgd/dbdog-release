# 升级脚手架登记

**规矩（家族军规 10）**：一次变更如果会让在网环境需要人工介入才能恢复正常
（改 env、补字段、跑一次性 SQL、手工重启……），那就不是「写进文档让运维照做」，
而是 `install.sh` / `upgrade.sh` 自己在升级时把它做掉；版本号看不出来的那种漂移，
还要在 `check-upgrade.sh` 里报出来（`pending_stack_config`），否则没人会去跑升级。

自愈逻辑写完就登记到本表：**从哪个版本到哪个版本需要它**。不是每两个版本都要立一条；
到期（在网环境全部越过下限）就按「删除清单」删干净——脚手架留着不删就是下一个人的负担
（军规 4：死记录直接删）。

## 怎么读这张表

- **覆盖区间**：装出「坏状态」的版本下限 → 自带修复的版本上限。上限之后**首装**的环境
  天然正确，只有上限之前装过、且还没跑过一次升级的环境需要脚手架。
- **可删条件**：判断依据永远是「在网环境是否都跑过一次 ≥ 上限的升级」，不是时间。
  拿不准就上机看判据列的那条命令，别猜。
- **删除清单**：删的时候要动哪几处，一处不落。

## 在册

### S1 · dbdog-web 缺 `DBDOG_APIKEY_ENC_KEY`

| 项 | 值 |
|---|---|
| 引入 | 2026-09-03，release `0ebbfc5`（自愈）+ `1ae376e`（探测） |
| 覆盖区间 | dbdog-web **≤ 0.1.24 时期装/升的环境** → 修复自 0.1.25 一代的升级起随任意模块升级生效 |
| 病症 | `etc/dbdog-web.env` 里该行是空的（发布模板派生自 web 仓 `.env.example`，一直没值），控制台「新建 API Key」直接报 `DBDOG_APIKEY_ENC_KEY 未配置或不是 32 字节 base64`（web 侧有意 fail closed） |
| 自愈 | `lib.sh: ensure_apikey_enc_key`——值缺失或解不出 32 字节才生成一把写回，合法值永不轮换 |
| 探测 | `lib.sh: pending_stack_config` → `check-upgrade.sh` 打进表格并退 10 |
| 判据 | 每台机 `grep '^DBDOG_APIKEY_ENC_KEY=' ~/dbdog/etc/dbdog-web.env` 是 44 位 base64 |
| 可删条件 | 在网环境全部满足上面的判据（即都跑过一次 ≥ 引入提交的升级） |
| 删除清单 | ① `pending_stack_config` 里这一项（表空了就整个函数连同 check-upgrade 的接线一起删）；② 合同测试里「待校准配置探测」那段。**`ensure_apikey_enc_key` 不删**——发布模板里这行永远是空的，首装生成是长期能力，不是脚手架 |
